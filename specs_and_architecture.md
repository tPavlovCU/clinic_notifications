# Техническое задание и Архитектура системы рассылок

Этот документ содержит полное техническое задание (ТЗ) и подробную архитектуру файлов для системы рассылок клиники, интегрированной с Yclients. Весь код пишется на языке **Go (Golang)**.

---

## Часть 1. Техническое задание (ТЗ)

### 1. Цель системы
Автоматизация отправки сервисных и маркетинговых уведомлений клиентам медицинской клиники на основе данных о записях (визитах) из CRM-системы **Yclients**.

### 2. Целевая аудитория и масштабируемость
* **Количество активных клиентов:** До 1 000 человек.
* **Характер нагрузки:** Низкая, транзакционная. Пиковые нагрузки отсутствуют, обработка происходит во временных интервалах (каждые 10-15 минут).
* **Требование к ресурсам:** Минимальное потребление памяти и процессора для возможности дешёвого хостинга.

### 3. Каналы доставки сообщений
1. **WhatsApp** — основной канал (через сторонние REST API провайдеры, например, Green-API).
2. **Telegram Bot API** — альтернативный канал (если клиент активировал бота).
3. **SMS** — резервный канал (через SMS.ru или аналоги, если мессенджеры недоступны).

### 4. Бизнес-логика (Типы уведомлений)
* **Триггер 1: "Новая запись"** — отправляется немедленно после создания записи в Yclients. Содержит: дату, время, имя врача, адрес клиники.
* **Триггер 2: "Напоминание о визите"** — отправляется строго за 24 часа до назначенного времени приема.
* **Триггер 3: "Сбор отзывов"** — отправляется через 2 часа после планового окончания визита.

### 5. Функциональные требования
* **Опрос Yclients:** Периодический сбор измененных или новых записей по REST API.
* **Идемпотентность:** Защита от дублирования сообщений. Одно и то же событие по одной записи не должно отправляться дважды.
* **Гарантия доставки (Retry Policy):** При ошибках сети со стороны шлюзов (Telegram/WhatsApp) задача должна возвращаться в очередь для повторной отправки (до 3 раз с экспоненциальной задержкой).

## Часть 2. Системная архитектура

### 1. Компоненты системы
* **Go Application:** Монолитное приложение, совмещающее функции планировщика (Cron/Ticker), бизнес-логики и воркеров обработки очереди.
* **SQLite:** Легковесная встраиваемая база данных для хранения логов уведомлений, истории записей и их статусов.
* **Redis:** In-memory брокер сообщений для организации надежной асинхронной очереди задач.
* **Docker / Docker Compose:** Инструмент контейнеризации для развертывания связки Go + Redis на сервере одной командой.

### 2. Схема движения данных (Под капотом)
```text
[Yclients API] 
      │ (HTTP GET каждые 10 мин)
      ▼
[Go: Ticker / Fetcher] ──(Проверка дублей)──> [SQLite]
      │
      │ (Если новое событие: Кладёт задачу в JSON)
      ▼
[Redis: Message Queue]
      │
      │ (Асинхронно считывают воркеры)
      ▼
[Go: Workers] ──(Запрос отправки)──> [WhatsApp / Telegram / SMS API]
      │
      └───────(Обновление статуса: Успех/Ошибка)───────> [SQLite]
```

## Часть 3. Архитектура файлов проекта

Ниже представлена полная структура каталогов, необходимая для реализации проекта по стандартам Clean Architecture в Go:

```text
clinic-notifier/
├── cmd/
│   └── app/
│       └── main.go          # Точка входа. Сборка зависимостей и запуск приложения
├── internal/
│   ├── config/
│   │   └── config.go        # Парсинг переменных окружения и .env файла
│   ├── database/
│   │   └── sqlite.go        # Инициализация пула соединений с файлом SQLite
│   ├── domain/
│   │   ├── models.go        # Чистые бизнес-сущности (Запись, Сообщение, Статус)
│   │   └── services.go      # Бизнес-логика: фильтрация, валидация, логика триггеров
│   ├── queue/
│   │   └── redis.go         # Продюсер и Воркер для работы с очередью задач Redis
│   └── repository/
│       ├── sqlite_repo.go   # SQL-запросы: сохранение логов, проверка отправленных
│       ├── yclients_api.go  # HTTP-клиент для взаимодействия с API Yclients
│       ├── provider_wa.go   # Логика отправки через WhatsApp Gateway
│       └── provider_tg.go   # Логика отправки через Telegram Bot API
├── migrations/
│   └── 0001_init.sql        # Схема таблиц (уведомления, логи, настройки)
├── .env                     # Конфиденциальные токены, доступы, пути к БД (в .gitignore)
├── .gitignore               # Исключение .env, логов и бинарников из репозитория
├── Dockerfile               # Инструкция многоэтапной сборки Go-приложения
├── docker-compose.yml       # Манифест оркестрации контейнеров приложения и Redis
├── go.mod                   # Декларация зависимостей Go-модуля
└── go.sum                   # Контрольные суммы зависимостей
```

## Часть 4. Назначение модулей (Кратко для ментора)

1. **`cmd/app/main.go`**: Выступает в роли "главного конструктора". Он считывает конфиг, открывает файлы базы данных, поднимает Redis, создает экземпляры репозиториев и передает их в сервис логики. Запускает фоновые процессы.
2. **`internal/domain/models.go`**: Содержит структуры данных. Никакого исполняемого кода, только описание сущностей на Go (Data Models). Это ядро системы.
3. **`internal/queue/redis.go`**: Реализует паттерн "Producer-Consumer". Один метод кладет задачу в Redis (через `LPUSH`), другие методы (воркеры) в бесконечном цикле блокирующе читают задачи (через `BRPOP`), обеспечивая асинхронность.
4. **`internal/repository/`**: Изолирует внешние сетевые и дисковые операции. Если завтра изменится API WhatsApp или мы перейдем на другую БД, код в папке `domain` останется абсолютно нетронутым. Меняться будут только файлы в этой папке.
